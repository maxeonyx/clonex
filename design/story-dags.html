When the lines are merged, Git sees the same change made twice on two sides. CloneX's merge uses the replaced commit B3 as the base for tools/tb. The umbrella's side is exactly B3, so tools/tb simply becomes B3′, with no conflict (Q-S7b). U3 records, in the commit itself, that B3′ replaces B3, so every machine maps it down the same way: U3 is B3′ (Q-S2e). The record names commits, not labels (D1). How it is written is parked.

A plain git merge uses ρU(B1) as the base. Both sides changed the ledger since B1, differently, so it conflicts in .test-status.json, a file the umbrella never touched. And mapping the merge down without the replacement record gives a new tb commit merging B3 and B3′, which would put the bad history back into tb if anyone published it.

What this story demands: (candidate rule) a tool commit built on a replaced commit is regenerated on its replacement when mapped through a merge that records the replacement. This needs its own attack before it is trusted: who may record a replacement, and what if it is wrong (the forged-claim story).
